PRODUCTIONLINE01 - ASSET HIERARCHY AND VARIABLE DEFINITIONS
============================================================

Purpose
-------
Demo hierarchy for a beverage manufacturing process and OEE-oriented
telemetry. The hierarchy retains the supplied assets and adds the variable
definitions needed to demonstrate equipment and line monitoring.

IMPORTANT API NOTES
------------------
1. Variable definitions are reusable metadata. The API's CreateVariableDefinition
   accepts: name, dataType, unit, description.
2. createdAt and updatedAt are generated and returned by the service. They are
   NOT accepted in the create request. The API does not allow clients to set
   these timestamps.
3. A variable definition must first be associated with an asset type, and then
   assigned to an asset of that type.
4. The script creates the type-variable associations and assigns the variables
   to each asset.
5. Values such as RUNNING, STOPPED, IDLE and FAULT are represented as STRING
   because the supplied API schema does not define an ENUM data type.
6. Counters should be cumulative within the counter's defined reset scope.
   Rates are not counts. OEE calculations should use deltas from counters over
   the reporting window and handle resets/restarts.
7. OEE configuration (shift schedules, planned breaks, ideal rates/cycle times,
   product-specific rates) is not represented as telemetry variable definitions
   here. Store that as production/configuration data in the relevant service.

HIERARCHY
---------

    +-- Mixer_01 [Asset Type: MIXER]

VARIABLE DEFINITIONS
====================

Conventions:
- dataType is the API's string field. Suggested values below are FLOAT,
  INTEGER, BOOLEAN and STRING.
- "-" means dimensionless / not applicable.
- Timestamp fields below are variable-definition audit fields returned by the
  API, not telemetry variables.
- Every variable definition is created once and reused through type
  associations where appropriate.

A. PRODUCTION_LINE01
--------------------
Asset type: PRODUCTION_LINE

Variables:
1. line_status
   Unit: -
   Data type: STRING
   Definition: Current production-line state (RUNNING, STOPPED, IDLE, FAULT).

2. total_good_bottles
   Unit: bottles
   Data type: INTEGER
   Definition: Good finished bottles produced by the line; cumulative counter.

3. total_rejected_bottles
   Unit: bottles
   Data type: INTEGER
   Definition: Rejected finished bottles attributed to the line; cumulative counter.

4. total_bottles
   Unit: bottles
   Data type: INTEGER
   Definition: Total finished bottles produced by the line; cumulative counter.

VARIABLE DEFINITION AUDIT FIELDS
================================
For every variable definition created by the script, the service response
contains:
- id: UUID generated by the service
- name: variable name
- dataType: data type
- unit: engineering unit
- description: variable description
- createdAt: creation timestamp generated by the service
- updatedAt: last-update timestamp generated by the service

The create API request does not accept createdAt or updatedAt. They cannot be
pre-populated by this script. They can be inspected using GET /variables or
GET /variables/{id} after creation.

OEE IMPLEMENTATION NOTES
========================
- Availability = Operating Time / Planned Production Time.
- Performance = Ideal Cycle Time * Total Count / Operating Time.
- Quality = Good Count / Total Count.
- OEE = Availability * Performance * Quality.
- Planned production time and planned breaks come from schedules, not machine
  telemetry.
- Ideal cycle time / ideal rate is product- and equipment-specific configuration,
  not a measured process value.
- For batch equipment, define a batch as the production unit and use ideal
  seconds per batch or batches per hour.
- For Pump_0, define whether the OEE production unit is litres or completed
  transfer cycles. Do not mix units in one calculation.
- For line OEE, use the line's own planned time, final output, good output and
  ideal line rate. Do not take a simple average of child-machine OEE values.
- A process parameter outside its setpoint is not automatically a rejected
  product. Apply explicit quality acceptance rules.
